# Phase 2.5 — Product polish and notification inbox

**Status:** done  
**Goal:** Make the existing MVP feel like a product and become demo-ready. **Not** a new feature phase.

## Why this phase existed

Phase 2 made the workflows real. The UI still felt like a functional prototype:

- Dashboards mixed live data with vote/document cards that had no product behind them
- Notifications were written to Postgres but residents had no inbox
- Admin status changes did not tell the reporter
- Empty, loading, and error states were incomplete
- Mobile used a desktop header and a truncated bottom nav

A live demo (manager → urgent announcement → resident bell → report issue → admin in progress → resident inbox) has to feel intentional.

## What shipped

### Resident home

- Greeting (`Good morning/afternoon/evening`, first name)
- Building name and apartment
- Featured important/urgent announcement + Read
- My issues with status badges
- Quick actions: Report a problem, Announcements, Notifications
- Voting and Documents as **Coming soon** (not fake lists)
- Recent notification activity from the database

### Admin home

- Real counts: residents, open issues, active votes, documents
- Vote/document counts labeled coming soon (numbers are real seed rows; workflows are not)
- Recent announcements, recent issues, recent activity
- Quick actions: create announcement, view issues, view residents
- Read-only resident directory (`/admin/residents`) from memberships

### Manager home

- Totals: buildings, residents, apartments, open issues
- Building cards: name, address, residents, apartments, open issues → `/manager/buildings/[id]`
- Building summaries use `groupBy` instead of N+1 count queries per building

### Notification center

- Bell on authenticated shells with **real** unread count
- Desktop dropdown, mobile drawer
- `/notifications` inbox for the signed-in user (shared route, not resident-only)
- Mark one as read; mark all as read
- Clicking a row marks it read and follows `data.announcementId` / `data.issueId`

### Issue / announcement UX

- Status filters with clearer labels
- Admin issue list prioritizes `REPORTED` then `IN_PROGRESS`
- Shared history component: “Reported”, then “Status changed to In Progress” + actor + time
- Urgent/important cards use a left accent border

### Platform quality

- Empty states, skeletons, `app/error.tsx`, `app/not-found.tsx`
- Mutation errors mapped through `toActionError` (no Prisma text in the UI)
- Responsive nav per role; tables converted to cards on manager building detail
- Issue status change notifies the **reporter**

## How notifications work (2.5)

Ownership is always the session user:

```ts
prisma.notification.findMany({ where: { userId: ctx.user.id } })
prisma.notification.findFirst({ where: { id, userId: ctx.user.id } })
```

If someone submits another user’s notification id, the row is not found. Tests cover that.

Reporter notify (no new enum):

```ts
type: "SYSTEM"
title: "Your issue is now in progress."
data: { issueId, kind: "ISSUE_UPDATE", status }
```

`lib/notifications/presentation.ts` maps that to the label “Issue update” without importing Prisma into client components.

`/notifications` sits outside `(resident)` so admins and managers can open the same path with their own shell (viewer kind from `getViewerKind`).

## Why these choices

- **Polish phase, not features:** voting UI would have delayed a convincing demo without proving the operating loop.
- **Reuse `SYSTEM`:** additive enums need migrations; JSON `kind` is enough until a dedicated type is required.
- **Shared `/notifications`:** putting the inbox only under the resident layout would hide admin “new issue” alerts.
- **Coming soon instead of seed votes on the resident home:** showing a vote card implied a workflow that does not exist.
- **Read-only resident directory:** the demo needs “View residents” without becoming a CRM phase.
